# Increment 6 — Persistent Causality and Consequences

## 1. Proposed playable result

A player starts a small adventure, offends a guard, rescues a villager, takes an item, and lets a deadline pass. They can leave those scenes, close the game during an unfinished encounter, and later resume from the same point. The guard's response, the villager's allies, the item location, the enemy's fate, and the deadline all agree with earlier actions. Command mode and the AI DM see the same current reality. The DM receives a short, relevant history, but cannot change that reality by narrating something different.

This is a plan for the later `to-tickets` pass, not an implementation issue list or a claim that increment 6 is already built. Keep the first demonstration compact: one authored consequence scenario, followed by proof that an existing generated schema-3 adventure can also be saved and resumed. A multi-session journey matters more than a larger map.

## 3. Scope and explicit boundaries

Deliver five player-visible capabilities together: durable event history; persistent relationships; a small deterministic deadline clock; reliable save/resume; and state-grounded DM memory. Support both command and AI play over the same authoritative transition path. The existing scene, journal, status, and conversation views should expose consequences only when the player could legitimately know them.

The first clock is a bounded authored track advanced by explicit time-bearing actions or an explicit `wait` action, with a documented time cost. No real-world clock, background scheduler, arbitrary “several days” interpretation, or general DM adjudication is required. Increment 7 can expand clocks and unexpected-action judgment after this narrow model works. Do not add a campaign calendar, new classes, broad relationship simulation, cross-adventure continuity, cloud saves, multiple devices, automatic migration of old save formats that never existed, or a general event-sourcing framework.

The sample consequence scenario should have at least two locations and three NPC roles: a guard who can be insulted or helped, a villager who can be rescued, and an ally whose later response reflects the rescue. Include one unique item, one defeatable enemy, and one deadline with visible warning and consequence. The player should still have a completable route after the deadline or a failed social interaction; the world may become harder or an ending less favorable without silently dead-ending. Reuse current combat and clue mechanics. If an `insult` interaction cannot be represented by the existing finite dialogue actions, add one narrowly defined conversation choice/effect rather than free-form state mutation by the DM.

## 4. Authority and transition contract

Treat a successful engine mutation as one committed transition. Define an internal transition result containing: stable action identity, typed domain events in causal order, the next canonical state, RNG position, and a state digest. A rejected action or read produces no durable world event, consumes no time or random draw unless the existing rules explicitly make it a committed attempt, and leaves the canonical state unchanged. An attempted social check is a committed mutation even when its roll fails; narration success or failure is separate.

The append-only event history records facts that happened: for example `relationship-changed`, `actor-relocated`, `actor-died`, `item-transferred`, `discovery-granted`, `clock-advanced`, `clock-threshold-crossed`, `check-resolved`, and `ending-chosen`. It should include sequence, cause/action ID, relevant entity IDs, and bounded payloads. Derive it at the same engine boundary as state changes; never mine rendered `clue` text, LLM prose, or a diff of arbitrary JSON. Keep presentation events and durable domain events distinct. Current structured state answers “what is true now”; history answers “how did we get here.” A history summary is a projection of those sources, not another store of facts.

For this small game, a save may contain a canonical checkpoint plus the append-only transition journal. Loading validates the document and version tuple, replays the journal through the correct deterministic runtime from the embedded adventure, and compares the resulting state, RNG position, sequence, and digest with the checkpoint. This provides a concrete integrity check without making checkpoint JSON a trusted bypass around engine rules. Set size/turn limits and identify the first divergent transition. If full replay becomes too costly later, add verified checkpoints as an explicit format revision. Never execute user-supplied scripts or trust an arbitrary saved state as an initial condition.

Ensure a transition is persisted exactly once before the next player prompt. Save only at settled engine boundaries: after the complete player action and its automatic opponent turn, and after a committed AI tool call even if subsequent narration fails. Do not persist half an attack, half an effect list, or a pending model response. After a disk write failure, report that the last action is not durably saved and stop accepting further mutations until the save succeeds or the player explicitly exits without saving. Atomic replacement in the same directory should keep the previous valid file usable after interruption.

## 5. Minimal relationship and clock model

**Relationships.** Add a finite per-NPC attitude tier (for example hostile, wary, neutral, friendly) plus authored reason codes, not an unrestricted numeric psychology score. Engine-owned effects change a specified actor's tier by one permitted step or set a specified tier under an explicit condition. Repeated insults or rescues must be idempotent where the source event is one-time; unrelated dialogue must not shift attitudes automatically. Guards and allies can condition authored replies, access, or clue offers on the tier and/or the causal milestone. Keep private reasons out of public scene text until revealed. An NPC death overrides dialogue and aid regardless of the tier.

**Clocks.** Define one or a few named integer tracks with an initial value, upper bound, thresholds, and typed one-time effects. Each time-bearing action declares a deterministic increment; `look`, status, journal, invalid commands, provider retries, and replay consume no time. An explicit `wait <amount>` uses a bounded unit and validates combat/terminal restrictions before advancing. Crossing a threshold emits one durable event and applies its effects once, even if a single action crosses multiple thresholds. The authored sample should show an enemy plan advancing, with visible evidence at the next appropriate scene and an alternate route still available. Validate clock IDs, bounds, references, threshold order, effect support, and progression traps before play.

**Content versions.** Add a versioned content contract for relationship and clock definitions, predicates, effects, and conditional prose. Prefer extending the current data runtime with a new schema/rules version only after a behavior map shows exactly what the scenario needs. Existing schema-3/rules-v4 adventures retain their behavior, with empty relationship/clock state under the new save wrapper. The authoring guide must distinguish persistent state, event history, private facts, and player-visible consequences. Do not let content inject functions, unbounded expressions, prompt instructions, or arbitrary field updates.

## 6. Save and resume product flow

Proposed CLI shape: `--save <new-or-existing-path>` during play for automatic checkpoints and `--resume <path>` to load one; exact flags can be fixed in the first delivery slice. A local `save` command may force a checkpoint and show its path, but an unfinished session must already be safe to close after each committed action. `quit` is an explicit in-world session termination in current rules; distinguish that from closing the process or choosing “save and leave,” so a player can continue an unfinished adventure. Victory and defeat saves may be opened for read-only reflection, but cannot resume gameplay mutations.

A version-1 save envelope should include: format and exact engine/rules/content identities; validated adventure snapshot and digest so a moved/deleted source is not needed; original seed, RNG algorithm and verified next position; session status; ordered committed transitions with action/tool input, dice draws, domain events, and resulting digest; checkpoint state and sequence; and optional bounded diagnostic metadata. Avoid storing credentials, raw provider responses, or authoritative prose summaries. Player text and private canon may appear in a save, so document local file privacy and use the same bounded parser approach as adventure/trace loading.

For resumed AI play, reconstruct the relevant DM context from the loaded state and allowed event projection. Persisting a full prior model transcript is neither necessary nor authoritative. Keep the existing one-mutation budget and failure-after-commit behavior. On startup show “resumed” identity, location, HP, clock status known to the player, last meaningful event, and offered actions; do not replay the introduction as though the adventure has just begun. If the source adventure has changed, resume from the embedded snapshot or reject by exact digest if an external file is explicitly supplied; never silently merge new content into a live save.

Separate modes strictly: a save cannot be supplied to `--replay`, and a trace cannot be supplied to `--resume`. Old format-1–4 traces remain readable with their existing tuples. New format-4 traces should still be exportable from an uninterrupted run; for a resumed run, either add an explicit trace segment/continuation format with verified linkage or document that trace export covers only the resumed segment. Resolve this before implementing the CLI, and include a test proving no diagnostic evidence is lost across a split session. Do not quietly splice format-4 traces into an invalid fresh-session replay.

## 7. DM memory and information boundary

Build DM context from the current scene, currently visible NPCs/items/actions, relevant relationship and clock state, and a bounded selection of important domain events. Rank by current location, involved speaker, open quest, and recent causality; keep stable ordering and a token/character budget. Project only what that speaker or the player can know. For example, the guard may react to an earlier insult, while another NPC cannot cite a secret theft they never witnessed or learned about. A private clock stage may affect world state before the player sees its clue; the DM should receive only the visible consequence.

The DM may narrate or paraphrase an event, but every factual claim in a deterministic fallback should be derived from the same projection. A hallucinated apology, resurrection, returned item, or missed deadline must not mutate state. Test tool selections and factual consistency rather than exact wording. Include a long gap and a model-context truncation test: removing old conversational prose must not erase the guard's attitude or resurrect a killed enemy. Keep prompt/tool version changes explicit and preserve the supported replay tuples.

## 8. Verification and acceptance scenarios

Use one seeded, multi-scene fixture as the main vertical slice. The scripted journey should: insult the guard; leave; rescue the villager; take the item; fight or defeat the enemy; advance the clock; save during unfinished play (including a separate mid-combat checkpoint); restart the process; return to the guard and ally; and finish one of two truthful endings. Check the same journey in command mode and scripted AI mode. A second journey should help rather than insult the guard, meet the deadline, and see different later dialogue/availability. Verify a generated schema-3 adventure can save/resume without acquiring invented clocks or relationship effects.

| Risk | Required focused evidence |
| --- | --- |
| Causal consistency | Every accepted mutation has one ordered durable event set; reject/read/ambiguous AI requests do not append or change state; repeated one-time effects do not duplicate. State, journal, scene, NPC reply, ending, and DM projection agree after leaving and returning. |
| Time and relationships | Boundary tests for every tier/threshold, multiple thresholds crossed at once, death overriding aid, failed check, blocked wait during combat, and non-time-bearing reads. Solvability tests cover deadline missed and NPC unavailable routes. |
| Random continuity | Save immediately before a social roll, between combat turns, and before item healing; resumed draws, HP, initiative, and effects exactly match an uninterrupted run for the same seed. |
| Storage and tampering | Round trip; moved/deleted source; changed source; truncated/oversized/duplicate-key save; unknown versions; altered snapshot/digest/journal/checkpoint/RNG; write failure and interruption before atomic replace. Load fails clearly and leaves the prior valid save untouched. |
| AI failure | Committed tool action persists once when narration/provider fails afterward; retry and resume cannot reroll or use a consumed item twice. Old conversational prose can be absent while relevant event memory remains. Hidden events never enter the wrong NPC/player projection. |
| Compatibility | Released schema-3 adventures and format-1–4 traces still load/replay; new saves never route through trace replay; generation output and validation remain unchanged until explicitly versioned. |

Run focused tests at each slice, then the canonical `npm.cmd run verify` with its seven ordered gates and zero-warning standard. Test the critical path through CLI input, runtime, saved file, process restart, and public/DM presentation; pure state tests alone do not prove resume. A clean-checkout/package test should start and resume with only tracked code plus a save created during that test. For manual handoff, provide checked-in input scripts, a seed, exact commands and expected output facts for an interruption/resume, a mid-combat resume, and a guard/deadline branch. Human review should assess whether the returning NPC reactions and elapsed-time cues make sense without developer explanation. Live-model evidence is separate from scripted verification; record model/prompt/content identity and any untested live cases.

## 9. Ordered delivery slices for later ticketing

These are dependency and review boundaries for `to-tickets`, not prewritten GitHub issues. Each slice should end in a playable or inspectable behavior with focused acceptance coverage. Split a slice further where independently testable, while preserving the end-to-end checks.

1. **Lock the consequence scenario and transition inventory.** Author the two-route script and enumerate each existing mutation, automatic effect, RNG draw, and state field that needs durable representation. Decide the save/trace continuation contract and version matrix before changing executable code. Capture uninterrupted seeded baseline journeys and released replay fixtures. Acceptance: the scenario has a route after a missed deadline and unavailable NPC; every planned state change maps to an event and existing/new rule.
2. **Record typed durable events at the engine boundary.** Add ordered domain events and transition IDs for the existing data runtime, including combat, checks, discovery, item, death, relocation, and ending changes. Keep current presentation and format-4 trace behavior. Acceptance: accepted versus rejected/read transitions and provider failure after commit are distinguishable; an end-to-end command journey produces the expected event sequence.
3. **Persist and resume existing adventures.** Implement the bounded save envelope, exact tuple validation, RNG checkpoint/reconstruction, atomic writes, CLI mode separation, and command-mode resume from embedded content. Acceptance: a generated schema-3 adventure and chapel both resume mid-journey and mid-combat with exactly the uninterrupted outcome; corrupt/tampered files fail before play; old traces replay.
4. **Add finite relationships through authored data.** Version the content schema/rules, validate tier predicates/effects, and wire one guard/ally consequence through command and scene/dialogue views. Acceptance: helping versus insulting leads to different later legal responses after save/reload; dead NPCs cannot help or speak; no effect is applied twice.
5. **Add the first deterministic clock.** Add authored thresholds and a bounded wait action/time costs; apply threshold effects through the same transition path. Acceptance: deadline met/missed routes are playable and visible, threshold events occur once, and read/rejected actions consume no time. Save/reload across the threshold agrees with uninterrupted play.
6. **Resume AI play with grounded memory.** Project relevant state/events through the information boundary, version prompt/tool contracts as needed, and re-enter AI mode without replaying the opening. Acceptance: scripted AI and local controls preserve one-mutation semantics across restart and provider failure; guard/item/death/clock references remain true after long context truncation; private facts stay hidden.
7. **Integrate and qualify.** Run complete multi-session command and scripted-AI journeys, malformed-save and compatibility suites, clean-checkout/package verification, a bounded live DM sample, and unfamiliar-player continuity review. Document save commands, privacy, version limits, recovery behavior, trace linkage, and actual test evidence. Acceptance: the exit criterion below is met or outstanding evidence is named explicitly.

## 10. Exit criterion

Increment 6 is complete when a player can suspend and resume a multi-scene adventure in a new process, including during an unfinished fight, and see the same legal actions, next dice outcomes, NPC relationships, item/actor fates, clock stage, and ending as an uninterrupted seeded run. Both command and AI modes must use the saved canonical state; the AI's bounded memory must keep important causality without leaking hidden knowledge or becoming an alternate authority. A generated increment-5 adventure must remain playable and resumable. Corrupt or incompatible saves fail safely, released adventures and traces remain readable, full verification passes, and manual/live evidence states its actual limits.
