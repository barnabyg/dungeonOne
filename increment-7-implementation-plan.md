# Increment 7 — DM Judgement and Adventure Dynamics

## 1. Proposed playable result

A player can try a sensible action that was not written as a dialogue topic or command choice: brace a passage with nearby furniture, lure a guard away, offer a scarce item as a bribe, or trail a moving witness. The DM interprets the wording and proposes a bounded action; the rules engine checks the visible targets and resources, resolves any dice, advances time, and records the consequence. The player can then leave, wait several days, resume, and find that routes, NPC responses, and the enemy's plan still agree with what happened. A failed attempt and a refusal to follow the expected quest route remain playable.

This is a plan for a later `to-tickets` pass, not GitHub issues or an assertion that increment 7 exists. Use one compact authored adventure to prove the mechanism before considering generated adventures. The aim is useful freedom in a small world, not a general simulation of every imaginable action.

## 3. Scope and the demonstration adventure

Create a new small, versioned authored adventure, preferably using the guard, witness, item, alternative route, and raider pressure established by `consequence-journey` without changing its released content digest. The new scenario needs three or four locations, one moving NPC, one guard, one physical obstruction, one expendable bargaining resource, one clock with an observable multi-day plan, and at least two attainable endings. The normal authored route and a route after each demonstrated failed improvisation must remain completable. Give the player a genuine reason to experiment: the short route can be obstructed, the guard can be diverted or bargained with, and the witness can move while the player chooses whether to follow.

The first supported families are **manipulate a visible obstacle**, **create a distraction**, **offer or deceive a visible NPC**, **follow a witnessed departing NPC**, and **wait a bounded number of days**. These are reusable action families with typed targets and resources, rather than a list of accepted English phrases. Show at least two materially different methods for one goal (for example, barricade a route with furniture or distract the guard to pass it), plus an improvised item use that is legal but is not the item's ordinary healing use. Existing attack, take, talk, and move actions continue to cover their current cases.

Keep fire, structural destruction, arbitrary crafting, unrestricted theft, hidden travel, economy, faction simulation, and open-ended NPC schedules outside the first mechanics slice. A request such as “burn the stone hall” must get a situation-specific, truthful adjudication: the stone cannot burn; if a visible flammable prop and a supported smoke/distraction profile exist, offer or resolve that narrower attempt only when the player's intent permits it. Never silently turn an attempted destructive act into success, or narrate a building's loss without state to represent it.

## 4. Judgement contract and authority

Define a versioned `AdjudicationProposal` containing a family/profile ID, target ID, optional resource ID, approach, and the player's bounded original intent. The DM may choose among profiles made available by the current validated scene. The engine is responsible for legality, difficulty, dice, time, resource consumption, and effects. The model cannot submit an arbitrary DC, script, text-to-state operation, target outside visibility, or newly invented fact. A command-mode `attempt ...` (final syntax to choose in the first delivery slice) should reach the same resolver using a deterministic parser/selection path; users without an API key must be able to play the complete sample.

Each profile declares the legal target capabilities, optional resource capabilities, prerequisites, one resolution category, time cost, and finite success/failure effects. Proposed initial categories are:

| Category | Engine behavior |
| --- | --- |
| Trivial | If prerequisites hold, commit the small stated effect without a roll. If it has no durable effect, clearly present it as descriptive color and do not invent a world event. |
| Impossible | Return the concrete physical or canonical reason and a possible nearby alternative. No roll, item consumption, or clock advancement. |
| Fixed check | Roll one documented d20 check against an authored DC and modifier. Apply exactly one success/failure branch; failed attempts can still cost time or a resource when the profile says so. |
| Opposed check | Roll player and NPC sides from authored modifiers; define ties in favor of the defender. Capture both draws and both totals in mechanics, save, and trace. |
| Reasonable improvisation | Choose a validated profile from the current capabilities; its result may set a short-lived situation condition, alter a route, move an actor, change a relationship, or spend a resource. This category is a routing decision, not permission for free-form effects. |

Add a narrow typed situation vocabulary where existing milestones are too permanent: for example, `passage-barricaded`, `guard-distracted`, and `smoke-visible`, each with an owner/target and a deterministic expiration condition or clock threshold. Situation IDs, targets, duration, and legal effects are declared in content and validated. A barricade must change connection availability and public scene text; distraction must change a guard's legal response or position; an offered item must actually leave inventory if accepted. Define what happens on failed checks, repeated attempts, dead/absent actors, consumed resources, active combat, terminal play, and simultaneous clock thresholds. Reject an unavailable proposal before any draw or mutation. A committed failed attempt has one event set, its stated cost, and no reroll through a paraphrase.

Treat the complete player attempt and any automatic consequence as one atomic transition. Order: validate proposal and present ambiguity if needed; resolve check; apply profile effects; advance the relevant clock; apply crossed thresholds in order; settle any resulting state; persist once; then narrate. No second model call can initiate another mutation in the same player turn. Keep NPC knowledge and player visibility separate: a covert distraction or deception is not automatically known by every NPC.

## 5. Content, clocks, and progression

Add a new supported schema/rules/engine tuple for adjudication profiles, target/resource capability tags, situation conditions/effects, NPC opposition modifiers, and day-based clocks. Prefer extending `ClueState` and `createChapelCluesRuntime` behind the new tuple. Make the action/profile vocabulary small and explicit. Reject unknown capabilities, broken references, non-terminating or contradictory effects, unbounded durations, duplicate aliases, impossible target/resource combinations, and actions that can remove every supported completion route. Do not reinterpret or migrate schema 1–5 files.

The sample clock should say what one unit means: **one day**. `wait days N` should accept a bounded N (for example 1–7), show the start and end day, and cross every intermediate threshold exactly once. Waiting in combat or after an ending is unavailable. Reads, invalid proposals, clarifications, provider retries, replay, and resumed startup consume no days. Short local actions need not each take a day; authored day costs for travel or major projects should be explicit. NPC movement and public warnings can be threshold effects, but the player only learns an off-screen change through a witnessed departure, a later scene, an NPC who plausibly knows, or an authored clue. Waiting beyond a terminal threshold should saturate or reject as specified; never wrap or repeat its effects.

Following an NPC is legal only after a witnessed departure and while an adjacent, traversable route remains. The engine may move the player along that route as one committed action; it cannot teleport to an unseen destination or skip a blocked connection. If the NPC is lost, dead, or beyond reach, explain why and leave the world consistent. One missed-deadline route must remain completable, even if the ending is worse. A refusal to help or leaving town should have an explicit truthful branch or route, rather than forcing the original quest script back onto the player.

Update positive progression analysis and route witnesses for the new predicates/effects. Because the analyzer already reports some dialogue effects as `analysis-incomplete`, do not treat `ok: true` as proof of solvability. Keep named executable witnesses for every ending, for missed day thresholds, for failed checks, and for a relevant NPC/resource becoming unavailable.

## 6. Player interface and AI behavior

Expose possible physical affordances in scene/inspection prose without printing a complete list of “correct” creative sentences. Command help should show the new action grammar and day unit. An ambiguous request should ask one focused question before a mutation (which target, item, or tactic), preserving the clock and RNG. Show authoritative category, prerequisites or refusal reason, rolls/DC or opposed totals, resource spent, clock change, and visible effect separately from DM prose. A rejected attempt should suggest a legal next move if one is evident from the current public scene.

The AI receives only currently visible target/resource IDs, bounded capabilities, relevant clock stage, and speaker-scoped history. It may interpret wording and choose one available proposal. It may not invent an affordance in a hidden room or ask for an unseen actor. After execution, narration is grounded in the resulting state and events; on provider failure, a deterministic fallback states what actually happened. The player must not need good prose to understand whether a barricade held, a bribe was spent, the guard noticed a deception, or a day passed. Record distinct prompt/tool versions for the new tuple, leaving historical replay behavior pinned to old versions.

## 7. Verification and exit evidence

Build a frozen “weird player behavior” suite spanning the roadmap's examples: attack the quest giver, refuse the quest, leave town, burn the quest location, deceive an ally, wait several days, and use an item for an unintended plausible purpose. Add barricade, distraction, bribe, follow, impossible/imprecise target, compound request, hidden target, consumed resource, dead NPC, and mid-combat attempts. For each case write down the intended adjudication category, legal state effect or refusal, clock cost, public explanation, and route to continue. Do not count a generic “unsupported” response as success where the sample content provides a legal capability.

Required evidence:

- End-to-end command and scripted-AI journeys through the built CLI, including two methods to bypass one obstacle, a failed check, a multi-day wait, an NPC departure/follow attempt, a missed threshold, a worse but truthful ending, and a save/process restart. State, scene, journal, DM history, and ending must agree.
- Exact seeded rolls and state/RNG equality between uninterrupted and split runs; no duplicate item use, threshold effect, or check after resume or narration failure. New-format trace segments must replay with the new tuple. Preserve the released schema 1–5 adventures, old saves, and trace formats 1–5 under their existing contracts.
- Boundary tests for visibility, capabilities, content validation, opposed-check ties, multiple thresholds in one wait, route obstruction/unblocking, situation expiration, actor death, stale proposals, time costs, provider failure, and malformed/tampered saves and traces. Test the critical UI → API/tool → engine → storage → resumed UI path, not just pure functions.
- A small live-model review with exact model, prompt/tool/content IDs and sanitized tool/outcome records. Review whether unfamiliar phrasings reach the correct profile and whether narration reports success/failure and costs faithfully. Scripted success does not qualify live judgment.
- A player test with at least one unfamiliar person who is encouraged to try actions outside the offered examples. Record the utterances, intended actions, actual outcomes, contradictions, recovery from refusal, and whether the consequences felt understandable. Avoid treating “finished the quest” alone as proof of freedom.

For a provisional increment exit gate, use a frozen set of at least 20 varied, previously unseen phrasings across the supported families and negative cases. Require at least 16 coherent category/target selections, **zero** unauthorised state changes or false success claims, and a demonstrable continuation after every supported failure branch. Report every miss by category rather than hiding a weak family in the aggregate. This is a narrow benchmark for the authored fixture, not a claim of open-world competence. Run focused checks as slices land, then the canonical `npm.cmd run verify` with seven ordered gates and zero warnings. Before claiming a playable release, build and start from a clean checkout and run a saved/resumed journey there. Manual handoff should give copyable PowerShell startup/resume commands, exact in-game inputs, expected results at each branch, and Ctrl+C only after the next `>` prompt.

## 8. Ordered delivery slices for `to-tickets`

These are dependency and review boundaries, not prewritten issues. Split a slice when it has a separately demonstrable outcome; keep each ticket's acceptance at the player-facing boundary where practical.

1. **Freeze the scenario and judgment matrix.** Author the small fixture design, two routes, day timeline, target/resource capability map, proposed categories, and expected handling of every weird-behavior case. Capture current schema-5 and replay baselines; specify the canonical action/trace/save representation and how mixed-mode trace segments will be treated. Deliverable: reviewed content and executable route witnesses for the existing route, plus a contract decision before runtime changes.
2. **Resolve one physical improvisation end to end.** Introduce the new schema/rules tuple, one typed proposal action, one obstacle profile, validation, command syntax, AI tool, mechanics, domain events, and save/replay support. Demonstration: barricade a visible passage, leave, resume, and find the route and scene changed. Rejected/ambiguous proposals leave state, clock, and RNG untouched.
3. **Add checked and opposed judgments.** Add fixed and opposed profiles with authored modifiers/DCs, deterministic rolls, a failed-attempt cost, and retry rules. Demonstration: lure or deceive a guard by two phrasings, see both outcomes, and continue through an alternate route. Cover ties, absence/death, one-mutation budget, and AI failure after commit.
4. **Make resources and situations matter.** Permit an authored carried item to serve as a bribe or distraction resource, with bounded consumption and situation duration/expiration. Demonstration: the item leaves inventory once, the NPC or route changes for the declared interval, and a revisit reflects expiration. Preserve ordinary healing-item semantics in old content.
5. **Advance days and move the world.** Add explicit day-unit clock content, bounded multi-day wait, threshold-driven NPC movement, public warnings, and witnessed following. Demonstration: on-time and late routes, following and losing the witness, save/resume across a threshold, and a viable late ending.
6. **Ground AI judgment and player presentation.** Offer only visible profiles, ask focused clarifications, render exact mechanics and current facts, project knowledge safely, and provide useful fallback text. Demonstration: live and scripted utterances with unexpected wording lead to the same authoritative results as command mode; no hidden or false claim reaches the player.
7. **Qualify the complete flexible adventure.** Run the frozen suite, route witnesses, full verification, clean-checkout save/replay, live review, and unfamiliar-player exercise. Record observed failures and resolve any that violate the exit gate; retain separate evidence for automated safety, model interpretation, and player experience.

## 9. Boundaries and handoff questions

Do not add generic model-authored state patches, arbitrary JavaScript in adventure files, unrestricted DC selection, a full D&D skill list, campaign economy, real-time scheduling, procedural NPC planning, or automatic schema-6 generation in this increment. Keep old content, saves, and traces readable through their pinned runtimes. If a change would make released data unreadable, stop and obtain explicit approval with affected versions and a migration proposal.

The first ticket should settle three narrow interface choices with a concrete example: the command grammar for an improvised attempt, the exact day-cost policy for major actions, and whether a mixed command/AI resumed trace is supported now or documented as a separate diagnostic limitation. These choices do not change the authority rule: the engine alone decides durable outcomes.
